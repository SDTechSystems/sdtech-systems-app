# Etapa 1 · Base (servidor, base de datos, login, clientes y catálogo) — Plan de implementación

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Dejar en producción `panel.sdtechsystems.dev`, protegido con Cloudflare Access, donde Juan administra clientes y el catálogo de precios, con los datos en Cloudflare D1 y sincronizados entre celular y computador.

**Architecture:** Un solo Cloudflare Worker sirve el panel (SPA React en `dist/`) y su API `/api/admin/*`, y responde distinto según el host (`panel.` o `clientes.`). D1 es la única fuente de datos. El Worker aplica sus propias migraciones al primer uso, así el despliegue por Git (Workers Builds) no necesita pasos manuales de base de datos. La identidad viene del JWT de Cloudflare Access, que el Worker verifica.

**Tech Stack:** TypeScript, React 18 + Vite + Tailwind 3 + shadcn/ui (copiados de `SDTechSystems/sdtech-imports`), react-router-dom 6, @tanstack/react-query 5, lucide-react, sonner, `jose` (JWT), Cloudflare Workers + D1 + static assets, wrangler 4 (dev), vitest 4 con `node:sqlite` como sustituto de D1 en pruebas.

**Spec:** `docs/superpowers/specs/2026-11-25-sdtech-systems-app-design.md` (§ 5, § 6.2, § 6.3, § 6.13 en parte, § 8, § 9 y § 11 etapa 1).

Las etapas 2 a 6 del § 11 tendrán su propio plan, escrito justo antes de construirlas, sobre lo que deja esta.

## Global Constraints

- Node 22 (`.node-version` = `22`); npm.
- Montos enteros: COP en pesos, USD en centavos. Una sola moneda por registro (`'COP' | 'USD'`), por defecto `'COP'`.
- Zona horaria `America/Bogota`; teléfonos con indicativo, `57` por defecto.
- Hosts: panel `panel.sdtechsystems.dev`, portal `clientes.sdtechsystems.dev`. `workers_dev: false`.
- Roles: `owner` (todo) y `collaborator` (sin precios, pagos, catálogo ni ajustes).
- Ningún correo, clave ni ID de Google/Access en el repositorio: `OWNER_EMAIL`, `ACCESS_TEAM_DOMAIN` y `ACCESS_AUD` son secretos del Worker, puestos en el panel de Cloudflare. En desarrollo van en `.dev.vars` (ignorado por git).
- Interfaz en español. Identificadores de código en inglés.
- Colores: `--sd-cyan #00BDE8`, `--sd-blue #2563EB`, `--sd-ink #07111F`, `--sd-muted #A7B9CD`. Logo: `SDTechSystems/portfolio/public/brand/{logo-horizontal.png,symbol.png}`.
- Cada mutación deja una fila en `activity_log` con el correo de quien la hizo.

## Review Focus

1. **API del panel sin login.** Una petición a `/api/admin/*` sin JWT válido de Access, o por el host `clientes.`, nunca devuelve datos: 401 o 404. Prueba en Task 3 y Task 4.
2. **Teléfonos escritos de mil formas.** `"305 814 7293"`, `"+57 305-814-7293"`, `"3058147293"` y `"(305) 8147293"` quedan como `"573058147293"`; `"+1 (212) 555-0100"` queda `"12125550100"`; texto sin dígitos da `null`. Prueba en Task 1.
3. **Precios con separadores.** `"650.000"`, `"$ 650.000"` y `"650000"` → `650000` COP; `"1.234,56"` y `"1234.56"` en USD → `123456` centavos. Prueba en Task 1.
4. **Búsqueda con tildes y mayúsculas.** Buscar `"maria"` encuentra a `"María Gómez"`, y `"GOMEZ"` también. Prueba en Task 4.
5. **Peticiones cruzadas desde otro sitio.** Una mutación (`POST`, `PATCH`, `DELETE`) sin `content-type: application/json` responde 415, para que una página ajena no pueda enviar formularios con la cookie de Access. Prueba en Task 4.

### Task 3: Login con Cloudflare Access, roles y usuarios

**Files:**
- Create: `worker/auth/access.ts`, `worker/auth/session.ts`, `worker/http.ts`, `worker/activity.ts`, `worker/api/me.ts`, `worker/api/users.ts`, `test/access-keys.ts`
- Test: `test/auth.test.ts`, `test/users.test.ts`

**Interfaces:**
- Consumes: `Env`, `ensureSchema`, `createTestDb` (Task 2).
- Produces:
  - `verifyAccessJwt(token: string, env: Env, jwks?: JWTVerifyGetKey): Promise<{ email: string } | null>`
    - Usa `jose.jwtVerify` con `issuer: \`https://${env.ACCESS_TEAM_DOMAIN}\``, `audience: env.ACCESS_AUD` y, por defecto, `createRemoteJWKSet(new URL(\`https://${env.ACCESS_TEAM_DOMAIN}/cdn-cgi/access/certs\`))`, en caché a nivel de módulo.
  - `type Session = { email: string; role: Role }`
  - `authenticate(request: Request, env: Env, jwks?: JWTVerifyGetKey): Promise<Session | Response>`
    1. Si `ACCESS_AUD` no está y `DEV_AUTH_EMAIL` sí, usa ese correo (solo desarrollo).
    2. Si ninguno está, responde 503 `{ error: 'access_not_configured' }`.
    3. Lee el token de `Cf-Access-Jwt-Assertion`; si falta o no es válido, responde 401.
    4. Si el correo coincide con `OWNER_EMAIL` (sin distinguir mayúsculas), el rol es `owner` y lo guarda en `users` con `INSERT OR REPLACE`.
    5. Si no, busca el rol en `users`; si no está, responde 403 `{ error: 'not_allowed' }`.
  - `requireRole(session: Session, role: Role): Response | null`: devuelve 403 cuando el rol no alcanza (`owner` ≥ `collaborator`).
  - `json(data: unknown, status = 200): Response`, `error(status: number, code: string): Response`, `readJson<T>(request: Request): Promise<T | Response>` (415 si el content-type no es JSON, 400 si el cuerpo no parsea).
  - `logActivity(db: D1Database, actor: string, entityType: string, entityId: string, action: string, detail?: unknown): D1PreparedStatement`. Devuelve la sentencia para incluirla en el mismo `batch` del cambio.
  - Rutas:
    - `GET /api/admin/me` → `Me`.
    - `GET /api/admin/users` → `{ users: { email, role, name }[] }`. Solo owner.
    - `POST /api/admin/users` `{ email, name? }`: crea un `collaborator`. Responde 201, o 409 si ya existe.
    - `DELETE /api/admin/users/:email`: quita un `collaborator`. No se puede borrar al dueño (400 `cannot_remove_owner`).
  - Handlers: `handleMe(req, env, s)` y `handleUsers(req, env, s, path)`, todos con la firma `(request: Request, env: Env, session: Session, path: string[]) => Promise<Response>`.

**Files:**

- Produces:
  - `export default { fetch(request: Request, env: Env, ctx: ExecutionContext): Promise<Response> }`. Llama a `ensureSchema(env.DB)` antes de atender `/api/*`.
  - Enrutamiento:
    - **host `clientes.sdtechsystems.dev`:** toda ruta responde con `renderPortalPlaceholder()`: HTML 200 con logo, «SD Tech Systems · Página de seguimiento de clientes», `X-Robots-Tag: noindex` y `Referrer-Policy: no-referrer`. `/api/admin/*` en este host → 404.
    - **cualquier otro host:**
      - `/api/admin/*` → `authenticate` y despacho por el primer segmento (`me`, `users`, `clients`, `catalog`). Si no existe → 404 `{ error: 'not_found' }`.
      - Lo demás → `env.ASSETS.fetch(request)`.
  - API de clientes (`handleClients`):
    - `GET /api/admin/clients?q=&archived=0|1` → `{ clients: Client[] }`, ordenados por nombre. `q` filtra con `search_text LIKE '%' || searchKey(q) || '%'`.
    - `GET /api/admin/clients/:id` → `{ client: Client, activity: ActivityEntry[] }`, con las últimas 50 entradas. Tipo: `ActivityEntry = { at; actor; action; detail: unknown }`, agregado a `shared/types.ts`.
    - `POST /api/admin/clients` → 201 `{ client }`.
    - `PATCH /api/admin/clients/:id` → `{ client }`. Campos parciales; `archived: boolean` archiva o restaura.
  - Validación:
    - `name` recortado y no vacío; si no → 400 `name_required`.
    - `phone` pasa por `normalizePhone`; si trae texto pero queda `null` → 400 `invalid_phone`.
    - `email` debe contener `@` → si no, 400 `invalid_email`.
    - Los demás campos se recortan, y si quedan vacíos se guardan como `null`.
    - `search_text = searchKey(name, company, phone, email, document, city)`.
    - Inexistente → 404.
  - Sesiones: los dos roles pueden leer y escribir clientes.
